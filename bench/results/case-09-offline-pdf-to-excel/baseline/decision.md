# Decision

## Recommendation: Adapt

This is worth pursuing as a focused Debian-first offline review workflow. It is not worth building as a general-purpose PDF-to-Excel engine from scratch. Reuse existing extraction, OCR, and table-structure components, then own the part that is still fragmented: one local desktop flow that shows the proposed table, links every cell back to the page, flags uncertainty, preserves raw text, and exports Calc-friendly data.

The strongest evidence is the split in current tools. [Tabula](https://tabula.technology/) already gives Linux users region selection, preview, and CSV/Excel export, but its documentation explicitly excludes scanned PDFs and its latest site release is from 2018. [Excalibur](https://excalibur-py.readthedocs.io/en/master/) adds a convenient local web UI over Camelot, with the same text-PDF limitation. [Camelot](https://github.com/camelot-dev/camelot) now documents deterministic parsers plus optional Table Transformer/OCR for scans, CSV/Excel export, multi-page stitching, and quality metrics, but it is a library without the review workflow. [OCRmyPDF](https://packages.debian.org/bookworm/ocrmypdf) and Tesseract make local OCR practical on Debian, but OCRmyPDF produces an OCR layer rather than a table or spreadsheet.

[Docling](https://docling.ai/) is the most useful general local building block for mixed and scanned documents: it advertises offline operation after model caching, OCR, layout, and table detection, and its [table export example](https://docling-project.github.io/docling/_generated/examples/export_tables/) writes detected tables through pandas to CSV/HTML. It still does not provide the requested native preview/editor and typed XLSX workflow. [Microsoft's Table Transformer](https://github.com/microsoft/table-transformer/blob/main/README.md?plain=1) likewise recognizes table structure from images but needs OCR or PDF text separately to populate cell content.

There is direct proof that the workflow is useful. [openstan](https://openstan.org/) ships a Debian package for a local/offline bank-statement product with side-by-side review and Excel/CSV/JSON export, but supports a defined set of UK banks. [PDFcsv](https://github.com/stexz01/pdfcsv) offers Linux support, coordinate-based column detection, live preview, and CSV/XLSX output, but its README calls the GUI future work and does not document OCR. [PDF Workbench](https://github.com/Iamakashgaur/pdf-workbench) demonstrates native/scanned/mixed routing, Tesseract, preview, CSV/XLSX, and reconciliation, while acknowledging that its generic path is bounded by supplier-specific layouts. [Anchor](https://anchor.aidenpaleczny.com/) is the closest current product match: local OCR and vision extraction, Excel/CSV, source-cell highlighting, and confidence colors. Its published support is Windows and Apple Silicon macOS only, with a beta Elastic License 2.0 release, about 3.5 GB of model files, and first-run internet setup. That leaves a real Debian packaging and open-source integration opportunity, while proving the workflow itself is not novel.

The problem is technically hard enough that review must be part of the product. The [TabSniper paper](https://arxiv.org/abs/2412.12827) describes bank statements as varying across banks, mixing scanned and electronic PDFs, spanning pages, and containing dense multi-line rows; it reports that existing structure recognizers miss long tables and discusses failures on tilted scans. The product should therefore measure and expose uncertainty instead of presenting extraction as guaranteed. [LibreOffice's Calc guide](https://books.libreoffice.org/en/GS75/GS7503-GettingStartedWithCalc.html) warns that CSV dates and decimal numbers can be interpreted according to the current locale, so a reliable export should write typed XLSX cells with explicit formats, ask for locale/decimal conventions, and retain the original recognized string beside each normalized value.

For the proposed integration, first verify that the chosen host has an extension point. [PDF Arranger](https://github.com/pdfarranger/pdfarranger) is a maintained GPL-3 Python/GTK Linux utility with page thumbnails and a Debian-friendly stack, but its documented scope is page manipulation. [PDFsam Basic](https://pdfsam.org/pdfsam-basic/) is a maintained local Linux Java utility, but its Basic scope is split/merge/page operations. The safest architecture is a host-neutral local worker/library with an optional host action; keep OCR/ML in an optional subprocess or package so a small PDF utility does not inherit a multi-gigabyte model or fragile runtime.

The first release should do the following:

1. Route each page as text, image, or mixed; use pdfplumber/Camelot/Tabula-style geometry for text and Tesseract plus a structure model or Docling for scans.
2. Let the user draw or adjust a region, show the table grid before export, and click a cell to highlight its source page/bounding box.
3. Store each cell as raw text, normalized typed value, source page/box, and confidence. Flag ambiguous digits, signs, dates, merged cells, and low-confidence OCR for correction.
4. Export XLSX and CSV. Put typed values and explicit number/date formats in XLSX; preserve raw values/provenance in a separate sheet or adjacent columns. Never silently drop rows.
5. Add document-family presets and validation rules. For statements, row counts, opening/closing balances, running balances, and totals are stronger checks than a generic confidence score.
6. Test first on a redacted corpus from two or three target banks/brokerages plus one corporate-report family, with text, scanned, mixed, multi-page, borderless, wrapped, and rotated cases. Track cell accuracy, row recall, unflagged error rate, correction time, and export time.

Use existing software instead if the real requirement is occasional clean text-PDF extraction; Tabula already handles that locally. Stop or narrow the build if the requirement expands to arbitrary layouts, handwriting, many languages, or guaranteed accounting-grade accuracy on unseen documents. The worthwhile wedge is a small set of supported document families where every exported value can be checked locally and every failure is visible.
