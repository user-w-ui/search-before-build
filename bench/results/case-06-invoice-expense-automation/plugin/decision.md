# Decision

## 必要性检查

| 门槛 | 结论 | 基础 |
| --- | --- | --- |
| 有具体问题 | 通过 | 事实：票据来自 Outlook、微信/支付宝导出和手机照片，月量 50–150 张。 |
| 功能解决问题 | 通过 | 事实：目标是字段抽取、提醒、去重、校验和 Excel；推断：人工复核会降低错入账风险。 |
| 交付形态合适 | 通过 | 事实：Windows 或家用 Linux 私有部署满足数据边界。 |
| 现有方式有明显摩擦 | 通过 | 事实：当前需要手工整理散落附件和纸质票据。 |
| 新建优于直接采用 | 未完全通过 | 推断：成熟组件和相近工作台已存在，从零开始的收益有限；但本地收集与动作门仍有组合缺口。 |

## 推荐

**Adapt**

FP 报销信息整理识别系统已经覆盖最接近的中文发票工作台：本地存储、识别后编辑、报销流程和 Excel 导出。PaddleOCR 可以承担本地识别层，invoice2data 可作为数字 PDF 的确定性模板路径，Auromix 的原件备份、存疑清单和“一笔消费一行”规则可复用。需要补的是 Outlook 受控收集、统一去重索引、低置信度停留在待复核、以及发送邮件/删除原件/提交报销三个独立点击确认门。

百度、阿里云和腾讯云的官方 API 对中国增值税及交通票据的字段覆盖更完整，但都把票据送到托管服务，和当前隐私约束冲突。Invoice Manager 的原图预览和 OCR/LLM 冲突对比值得借鉴；外部 LLM 不能成为默认路径。

最大未知是用户自己的 PDF、手机翻拍、火车票和出租车行程单样本在本地 CPU 上的字段准确率与处理时间。应先用脱敏样本做验收，再决定是否扩大票种和自动化边界。
