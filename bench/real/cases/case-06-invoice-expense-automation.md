# Case 06 · 发票识别与报销自动化（assess，中文办公场景）

| 项 | 值 |
| --- | --- |
| 技能（B 臂） | `search-before-build-assess` |
| 模拟用户语言 | 简体中文 |
| 补充材料 | 无 |
| 真实需求来源 | [Friday issue #1：发票与报销自动化](https://github.com/hunanjay/friday/issues/1)（公开 feature request；运行时以页面内容为准） |
| 对比焦点 | 中文办公场景、OCR/文档解析生态、合规与 Action Gate、个人助手与 SaaS 的取舍 |

## 来源与考察点

社区 issue 描述了真实的办公摩擦：电子发票散落在 Outlook 附件、微信/支付宝导出的 PDF 和纸质小票照片里，用户需要手工录入发票代码、号码、金额、日期，再整理报销单。原 issue 还提出了重复发票唯一索引、买方抬头与 90 天期限校验、邮件抓取、日历行程关联、`.xlsx`/`.pdf` 导出，以及发送报销邮件前的二次确认。

本 case 把它收敛成一个个人办公工具，考察 agent 是否能区分“识别和整理发票”与“自动替用户发邮件/提交报销”的风险边界，并检索中文发票 OCR、通用文档解析、开源自部署方案和商业 API，而不是只列几个 OCR 模型名称。

## 用户 prompt（两臂原样输入）

```text
我想做一个给自己用的发票和报销助手。发票现在散落在 Outlook 邮件附件、微信/支付宝导出的 PDF，还有手机拍的纸质小票里。我希望把文件丢给它后，自动识别发票号码、金额、日期、买卖双方和报销类别，发现重复票或抬头不对时提醒我，再按月份导出 Excel 报销明细。数据最好留在自己的电脑或私有服务器上，发邮件给财务前必须由我最后确认。这个东西值得自己开发吗？
```

## 澄清脚本（两臂通用，仅回答被问到的问题）

1. 输入规模与格式 → `每月大概 50 到 150 张，PDF 和手机照片各一半，偶尔有火车票和出租车行程单。`
2. 运行环境与隐私 → `Windows 笔记本和一台家里的 Linux 小服务器都可以，公司的发票不允许上传到陌生的云服务；可以接受本地识别慢一点。`
3. 必须准确的字段与人工介入 → `金额、发票号码、日期和抬头必须能让我逐张核对；识别不确定时给我看原图和可编辑字段，不要悄悄入账。`
4. 报销流程边界 → `先做收集、去重、校验和 Excel 导出就够了。邮件可以自动生成草稿，但发送、删除原件和提交报销都要我点击确认。`
5. 检索前确认（B 臂）→ `确认。`

## 两臂记录要点

- [ ] 候选清单：每臂最终提到的本地 OCR、发票解析库、私有化产品和云 API（名称 + 链接 + 定性），标出重合项。

- [ ] 是否把 OCR 置信度、人工复核和发送前确认当作流程约束，而不是只比较识别模型准确率。

- [ ] 来源覆盖：A 臂实际触达的平台；B 臂 coverage ledger 的实际内容；中文和英文查询词。
- [ ] B 臂内核：同一项目跨 GitHub、模型中心和包注册中心是否合并，字段缺失时是否降低置信度而不是杜撰合规结论。
- [ ] 两臂最终建议与理由链原文摘录。

## 对比焦点

1. 两臂是否发现成熟的 OCR/文档解析组件，并给出可以落地的“复用 + 薄封装”路径；
2. 哪一臂更认真处理本地部署、中文发票格式、人工复核和发送前 Action Gate；
3. 云 API、开源模型和完整报销产品的适用边界是否清楚；
4. 建议是 Build、Adapt、Use existing 还是 Stop，是否由真实流程成本而不是模型热度决定。
